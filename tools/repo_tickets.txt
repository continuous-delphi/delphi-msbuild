Title: Add generic MSBuild property pass-through (-Property)
Issue: #21
Status: closed
Labels: enhancement
Body:
## Background

Arose from evaluating `delphi-msbuild.ps1` as a replacement for an older batch
build system (`rad-buildfiles-shared`: `DelphiBuild.bat`,
`_SetDelphiBuildPaths.bat`) that compiles Delphi against trimmed, non-installed
per-version toolchains (no IDE install, `BDS`/`BDSLIB`/`BDSBIN` set manually).
All changes are opt-in and backward compatible.

## Problem

Only `Config`, `Platform`, `DCC_ExeOutput`, `DCC_DcuOutput`,
`DCC_UnitSearchPath` (append), and `DCC_Define` (append) can be set. There is no
way to pass arbitrary `/p:` properties. The batch sets `/p:DCC_BuildAllUnits=true`
and `/p:_EnvLibraryPath`, neither of which is exposed, and there is no general
escape hatch.

## Proposed

Add `-Property <hashtable>` (or `-Property <string[]>` of `Key=Value`), each entry
appended as `/p:Key=Value`. This single feature also covers `DCC_ResourcePath`,
`DCC_UsePackage`, `DCC_Namespace`, etc. -- the msbuild-side equivalent of the DCC
`--no-config` / `-R` / `-LU` requests filed against `delphi-dccbuild` (on the
msbuild path those are project / `DCC_*` property driven).

## Acceptance criteria

- [ ] Each `-Property` entry becomes a `/p:Key=Value` argument
- [ ] Values containing spaces or semicolons are quoted correctly
- [ ] Precedence vs the built-in properties is documented (explicit `-Property`
      should win or the behavior is clearly defined)

Title: Add -SkipRsvars and -MsbuildPath for caller-managed env / msbuild selection
Issue: #23
Status: closed
Labels: enhancement
Body:
## Background

Part of enabling `delphi-msbuild.ps1` to replace the older batch MSBUILD path
(`rad-buildfiles-shared`: `_SetDelphiBuildPaths.bat` does per-era framework
selection and manual `BDS` env). Opt-in and backward compatible.

## Problem

The script hard-requires `<RootDir>\bin\rsvars.bat` (exit 3), sources it, and then
runs a bare `& msbuild.exe` off `PATH`. Two issues:

- (a) Caller-managed environment. A caller may want to set `BDS` / `PATH` /
  `FrameworkDir` itself (exactly what `_SetDelphiBuildPaths.bat` does) rather than
  depend on rsvars. A pre-set-env path is required for any root that lacks rsvars.
- (b) No control over WHICH msbuild runs. It relies entirely on rsvars putting the
  correct .NET-Framework msbuild first on `PATH`. The batch selects `v2.0.50727` /
  `v3.5` / `v4.0.30319` per Delphi era explicitly, which matters for older
  (2007-2010-era) builds.

## Proposed

- `-SkipRsvars` (switch): do not require or source rsvars; build using the caller's
  current process environment.
- `-MsbuildPath <string>` (optional): invoke a specific `msbuild.exe` instead of the
  `PATH` lookup, enabling explicit per-era .NET-Framework selection.

## Acceptance criteria

- [ ] With `-SkipRsvars`, a root lacking `bin\rsvars.bat` builds using the current env
- [ ] With `-MsbuildPath`, that exact msbuild binary is invoked
- [ ] Existing behavior (require + source rsvars, PATH msbuild) is unchanged when
      neither switch is supplied

Title: Fix native-argument quoting for /p: values ending in a backslash
Issue: #24
Status: closed
Labels: bug
Body:
## Background

The MSBuild argument assembly in `Invoke-MsbuildProject` (source/delphi-msbuild.ps1)
hand-quotes several `/p:Key=Value` arguments by embedding literal double quotes into
the PowerShell string, e.g. `"/p:_EnvLibraryPath=`"$EnvLibraryPath`""`. These strings
are then passed to a native executable (`msbuild.exe`). PowerShell converts each array
element into a Windows command line, which `CommandLineToArgvW` re-parses into argv.

## Problem

When a value ends in a backslash (normal for a Windows directory path), the emitted
trailing `\"` is parsed as an *escaped literal quote*, not a closing delimiter. The
argument boundary is lost and the following arguments merge into the value.

Reproduced with a native arg-echo:

- Windows PowerShell 5.1 (a supported/tested target):
  `-EnvLibraryPath 'C:\Lib\' -Config Release Project.dproj` -> the exe receives a
  single argument `/p:_EnvLibraryPath=C:\Lib" /p:Config=Release Project.dproj` --
  the Config and project arguments are silently lost.
- PowerShell 7: arguments stay separate but the value keeps literal quotes
  (`"C:\Lib\"`) -- still wrong.

Affected hand-quoted sites (all in `Invoke-MsbuildProject`):

- `/p:DCC_UnitSearchPath="..."`  (always quoted; latent)
- `/p:DCC_Define="..."`          (always quoted; latent)
- `/p:_EnvLibraryPath="..."`     (always quoted; most exposed -- a bare path value)
- `/p:Key="Value"`               (generic -Property; quoted only when the value
                                  contains whitespace or a semicolon)

## Root cause it slipped

The unit tests assert the *string shape* of the captured `$Arguments` array against a
mocked `Invoke-MsbuildExe` (e.g. `Should -Contain '/p:_EnvLibraryPath="C:\Program Files\Lib"'`).
No test invokes a native executable, so the PowerShell-string-to-argv conversion --
the part that is actually broken -- is never exercised. The captured-string assertions
lock in the buggy shape.

## Proposed

- Stop hand-quoting `/p:` values. Pass the argument as `/p:Key=Value` (no embedded
  quotes) and let PowerShell perform native-argument quoting. A semicolon does not
  need quoting once the value is a single argv element (MSBuild splits on argv, not on
  `;`); spaces are auto-quoted by PowerShell. This is correct on PS 7 in all cases.
- For path-typed values (`-EnvLibraryPath`, `-UnitSearchPath`), trim a trailing
  backslash before assembling the argument -- MSBuild directory properties do not
  require it, and this removes the residual Windows PowerShell 5.1 failure for values
  that contain both a space and a trailing backslash (a known PS 5.1 native-quoting
  limitation).
- Minor: `-MsbuildPath` validation at the top-level guard uses
  `Test-Path -LiteralPath $MsbuildPath` without `-PathType Leaf`, so a directory
  passes the exit-2 check and fails later with a worse error. Add `-PathType Leaf`.

## Acceptance criteria

- [ ] `-EnvLibraryPath 'C:\Lib\'` yields an argument whose value the invoked exe
      receives as exactly `C:\Lib` (or `C:\Lib\`), with Config/Platform/project
      arguments preserved as separate argv elements
- [ ] The same holds for `-UnitSearchPath`, `-Define`, and generic `-Property` values
      that end in a backslash and/or contain spaces or semicolons
- [ ] `-MsbuildPath` pointing at a directory exits 2 (invalid arguments)
- [ ] A regression test invokes a real native arg-echo (a small compiled/echoing exe
      or equivalent) and asserts the argv the child process actually receives -- not
      the string shape of the `$Arguments` array
- [ ] Behavior verified under both Windows PowerShell 5.1 and PowerShell 7

Title: Pass MSBuild /p: properties via a response file to bypass command-line quoting
Issue: #25
Status: closed
Labels: enhancement
Body:
## Background

Follow-up to #24.  That fix stopped hand-quoting `/p:` values and trims a trailing
separator on path-typed values, which is correct on PowerShell 7 in all cases and on
Windows PowerShell 5.1 for everything except a generic `-Property` value that BOTH
contains whitespace AND ends in a backslash.  #24 turns that residual case into a
visible warning on PS 5.1 (it cannot be passed to msbuild.exe without corruption
because PS 5.1's native-argument quoting escapes the closing quote with the trailing
backslash).  This ticket removes the residual entirely.

## Problem

Command-line argument quoting is host- and version-dependent (Windows PowerShell 5.1
vs PowerShell 7 build the command line differently), so no single hand-assembled
argument array is bulletproof for arbitrary values across both engines.

## Proposed

Write the full `/p:` set to an MSBuild response file (e.g. a temp `args.rsp`, one
`/p:Key=Value` per line, no quoting) and pass `@args.rsp` to msbuild.exe instead of
individual `/p:` command-line arguments.  MSBuild reads a response file line-by-line,
so a value may contain whitespace, semicolons, quotes, or a trailing backslash with no
escaping -- this bypasses command-line quoting entirely and is correct on both PS 5.1
and PS 7.  Delete the temp file after the build (try/finally).

Consider applying this to all assembled `/p:` values (built-ins and `-Property`), or at
minimum to `-Property` and the path-typed values.  The project file, `/t:`, `/v:`, and
`/nologo` can remain direct command-line arguments.

## Acceptance criteria

- [ ] `/p:` properties are written to a temp response file and passed as `@file`
- [ ] The response file is deleted after the build (including on failure)
- [ ] A generic `-Property` value containing whitespace AND ending in a backslash
      reaches msbuild intact under BOTH Windows PowerShell 5.1 and PowerShell 7
      (verified by the native arg-echo regression harness added in #24)
- [ ] The PS 5.1 warning added in #24 is removed once the response-file path makes it
      unnecessary

Title: -Define / -UnitSearchPath clobber the project's config-scoped values (global /p: override)
Issue: #26
Status: closed
Labels: bug
Body:
## Problem

`-Define` and `-UnitSearchPath` are documented (README) as ADDITIVE: they emit
`/p:DCC_Define="$(DCC_Define);CI"` and `/p:DCC_UnitSearchPath="$(DCC_UnitSearchPath);..."`,
and the README states the `$(...)` prefix "preserves the defines/paths already set by the
project's PropertyGroups". In practice they do the opposite.

A standard Delphi project sets these in a CONFIG-conditional PropertyGroup, e.g.
`<DCC_Define>DEBUG;$(DCC_Define)</DCC_Define>` under `Condition="'$(Config)'=='Debug'"`.
Passing `/p:DCC_Define=...` makes DCC_Define a GLOBAL MSBuild property, and a global
property OVERRIDES a project PropertyGroup assignment -- so the config's `DEBUG` is never
prepended, and the `$(DCC_Define)` self-reference cannot resolve (it collapses to a stray
`$` token). Verified against msbuild.exe with a minimal project mirroring the pattern:

    A) global /p:DCC_Define="$(DCC_Define);CI"  -> effective DCC_Define = [$(DCC_Define);CI]  (DEBUG lost, stray token)
    B) env var DCC_Define=CI (no /p:)           -> effective DCC_Define = [DEBUG;CI]           (correct)

Impact: any MSBuild build using `-Define` silently loses the project's config defines
(DEBUG/RELEASE) and passes a garbage define. Tests that do not depend on DEBUG still pass,
which is why it went unnoticed. This bug predates the #24/#25 quoting work; the #25
response-file change did not introduce it (the `$(DCC_Define);CI` global-property approach
was always broken) but did make the semicolon crash visible, surfacing the deeper issue.

## Proposed

Pass the two APPEND-style DCC properties as ENVIRONMENT variables rather than global `/p:`
properties. An environment-derived property has the LOWEST MSBuild precedence, so the
project's config PropertyGroup runs and its `$(DCC_Define)` / `$(DCC_UnitSearchPath)`
self-reference resolves against the env value -- yielding the documented additive result.

- `-Define`         -> set process env `DCC_Define`         = (defines -join ';'); no /p:DCC_Define
- `-UnitSearchPath` -> set process env `DCC_UnitSearchPath` = (trimmed paths -join ';'); no /p:DCC_UnitSearchPath
- Save and restore any prior env value around the build (try/finally).
- OVERRIDE-style properties (Config, Platform, DCC_ExeOutput, DCC_DcuOutput,
  DCC_BuildAllUnits, _EnvLibraryPath, generic -Property) remain `/p:` via the response file.

## Acceptance criteria

- [ ] `-Define CI` on a project whose Debug config sets `DEBUG;$(DCC_Define)` yields an
      effective DCC_Define of `DEBUG;CI` (DEBUG preserved, CI added, no stray token)
- [ ] `-UnitSearchPath` likewise preserves the project's config-scoped search paths
- [ ] DCC_Define / DCC_UnitSearchPath are no longer emitted as `/p:` (response-file) args
- [ ] Prior values of the DCC_Define / DCC_UnitSearchPath env vars are restored after the build
- [ ] README `-Define` / `-UnitSearchPath` sections describe the env-var mechanism
- [ ] Verified end-to-end via a real build (radFormatterV2 BuildTest: DEBUG and CI both defined)

Title: Get-BuildOutputDir returns empty ExeOutputDir/DcuOutputDir for non-Win32 platforms
Issue: #27
Status: closed
Labels: bug
Body:
## Problem

On the MSBuild path, `Invoke-DelphiBuild` returns an empty `ExeOutputDir`
(and `DcuOutputDir`) for Win64 builds; Win32 populates both correctly. The
same defect affects every non-Win32 target (Linux64, macOS64/ARM64, etc.).

It only manifests when `-ExeOutputDir` / `-DcuOutputDir` are NOT passed
explicitly. When the caller supplies them, the values are echoed straight
back (source/delphi-msbuild.ps1:649-650) and are correct on all platforms.
The bug is in the fallback path that parses the output directory from the
captured MSBuild log.

## Root cause

`Get-BuildOutputDir` (source/delphi-msbuild.ps1:511) finds the Delphi
command-line compiler invocation in the MSBuild log and reads its `-E`
(exe output) and `-NO` (dcu output) switches. The line filter (line 521) is:

    Where-Object { $_ -match '[/\\]dcc32\.exe\s' }

The regex matches only `dcc32.exe` -- the Win32 compiler. MSBuild invokes a
platform-specific compiler for every other target:

    Win32   -> dcc32.exe        Win64      -> dcc64.exe
    Linux64 -> dcclinux64.exe   macOS64    -> dccosx64.exe
    macOSARM64 -> dccosxarm64.exe   (etc.)

For a Win64 build the compiler line is `...\dcc64.exe ...`, the filter finds
nothing, `Get-BuildOutputDir` returns early with both dirs `$null`, and that
null propagates up to the empty `ExeOutputDir` the caller sees. Win32 works
only because its compiler *is* named `dcc32.exe`. The `-E` / `-NO` switch
extraction below the filter is platform-agnostic and needs no change.

## Fix

Broaden the compiler-line filter to match any `dcc<target>.exe`:

    Where-Object { $_ -match '[/\\]dcc[^\s\\/]*\.exe\s' }

Update the function's leading comment (currently "Parse the dcc32.exe
invocation line...") and rename the `$dcc32Line` variable to reflect that it
now matches any DCC compiler. The DCCBuild engine is unaffected (it echoes
back the supplied `-ExeOutputDir` and never parses one from output).

## Acceptance criteria

- [ ] `Get-BuildOutputDir` parses a synthetic `dcc64.exe` log line and returns
      the populated ExeOutputDir (from `-E`) and DcuOutputDir (from `-NO`)
- [ ] The same holds for at least one other non-Win32 compiler (e.g.
      `dcclinux64.exe`)
- [ ] Win32 (`dcc32.exe`) behavior is unchanged
- [ ] An explicitly supplied `-ExeOutputDir` / `-DcuOutputDir` still round-trips
      (echo-back path is untouched)
- [ ] A dot-sourced Pester test drives `Get-BuildOutputDir` with synthetic
      non-Win32 fixtures and asserts the parsed dirs (tests/pwsh)
- [ ] All Pester tests pass

Title: Invoke-DelphiBuild returns empty ExeOutputDir for relative DCC_ExeOutput
Issue: #28
Status: closed
Labels: bug, regression
Body:
## Problem

`Invoke-DelphiBuild` (delphi-msbuild.ps1, scriptVersion 1.2.10) returns an EMPTY
`ExeOutputDir` on the result object even for a fully successful build
(`Success=True`, `ExitCode=0`, `Errors=0`). The other resolved-path fields
(`MsbuildPath`, `UnitSearchPath`) also come back empty in the same result, while
`RootDir` / `RsvarsPath` are populated.

The compiled binary IS produced correctly -- it just is not reported. For a project
whose `DCC_ExeOutput` is the IDE-default relative value `.\$(Platform)\$(Config)`,
the exe lands at `<ProjectDir>\<Platform>\<Config>\<name>.exe`, but the returned
`ExeOutputDir` is blank rather than that resolved absolute directory.

## Repro

Build any project with a relative `DCC_ExeOutput`:

    $r = Invoke-DelphiBuild -ProjectFile 'projects\scanner\cli\radCodeScanner.dproj' `
           -Platform Win64 -Configuration Release -BuildEngine MSBuild
    $r.Success       # True
    $r.ExeOutputDir  # '' (empty)  <-- BUG; exe actually at <ProjectDir>\Win64\Release\

Observed against radCodeScanner's CLI project (relative
`DCC_ExeOutput = .\$(Platform)\$(Config)`), Win64 Debug and Release: the exe is on
disk, `ExeOutputDir` is empty both times.

## Impact

Downstream consumers rely on `ExeOutputDir` to locate the binary without scanning
the filesystem -- the delphi-build docs explicitly sanction this ("Use ExeOutputDir
to locate the compiled binary without searching the filesystem"). When it is empty,
a `Join-Path $r.ExeOutputDir '<name>.exe'` throws
"Cannot bind argument to parameter 'Path' because it is null."

Concretely this currently breaks radCodeScanner CI: its `tools/validate-sarif.ps1`
dropped its own manual Win64 ExeOutputDir workaround (radCodeScanner v0.1.12.0,
commit 1e57393) specifically because this property was fixed at the time; the
property is empty again, so `BuildTest.bat` is red. radCodeScanner is holding that
workaround removal (no local re-add) pending this fix.

## Likely cause (to confirm)

The path-resolution that computes `ExeOutputDir` (and `MsbuildPath` /
`UnitSearchPath`) appears to have regressed for the relative-`DCC_ExeOutput` case
between the last known-good version and 1.2.10 -- possibly it only resolves an
ABSOLUTE / explicitly-passed `-ExeOutputDir` and returns empty when the project's
own relative output is used. Verify against the version that radCodeScanner
v0.1.12.0 validated on.

## Acceptance criteria

- [ ] On a successful build of a project using a relative `DCC_ExeOutput`
      (`.\$(Platform)\$(Config)`), `Invoke-DelphiBuild` returns a non-empty,
      absolute `ExeOutputDir` equal to the directory that actually contains the
      produced exe.
- [ ] Holds for Win32 + Win64 and Debug + Release.
- [ ] `MsbuildPath` / `UnitSearchPath` empties, if the same root cause, are fixed
      too (or documented as separate).
- [ ] A test/fixture covers the relative-`DCC_ExeOutput` case so this cannot
      silently regress again.
- [ ] Re-running radCodeScanner `BuildTest.bat` (its validate-sarif.ps1 unchanged)
      goes green against the fixed module.
